## متطلبات عامة (تسري عىل كل شاشة)

| المتطلب | التفاصيل |
|---|---|
| **RTL** | الواجهة عربية بالكامل — `dir="rtl"` من الجذر، وTailwind logical properties (`ms-`, `me-`) مش `ml-`/`mr-` |
| **التواريخ** | ميلادي، تنسيق `١٧ أغسطس` أو `2026-08-17` — اتفقوا عىل واحد |
| **الأرقام** | إنجليزية (`85%`) — أوضح في السياق التقني |
| **Loading states** | لكل شاشة — الـ workflows بطيئة بطبيعتها |
| **Error states** | اعرض الـ `error.message` من العقد، مش رسالة عامة |
| **Empty states** | مفيدة مش فاضية — "مفيش مراجعات معلّقة ✓" |
| **Optimistic UI** | ⚠️ **ممنوع** في شاشات الموافقة — دي عمليات حقيقية لا رجعة فيها |

## المتطلبات

**Keyboard-first** — هتراجع مئات الصفوف عىل مدار الشهور:
```
1–9      اختيار مرشح
Enter    تأكيد الأول
S        تخطي
X        مش من المتدربين
/        بحث يدوي في الروستر
←  →     تنقل
```

**عرض الفترات بصريًا** — شريط زمني بسيط يوري الحضور والانقطاعات.
ده بيساعد حاتم يقرر (لو الشخص قعد ٥ دقايق بس، غالبًا مش هو).

**التمييز البصري للفرق:** لو الفرق بين المرشح الأول والتاني أقل من ١٠٪،
لوّنه بالتحذير — دي الحالة الخطيرة.

# المرحلة ٢ (أسبوع ٨–١٢) — Approval Inbox

## أهمية الشاشة دي

**ده المكان الوحيد اللي بيخرج منه أي فعل للعالم الحقيقي.**
رسالة اتبعتت غلط = مشكلة مع متدرب حقيقي. الوضوح هنا أهم من الجمال.

## البيانات

```
GET /api/approvals?status=pending
```
```json
{
  "approvals": [
    {
      "id": 301,
      "type": "send_messages",
      "created_at": "2026-08-17T20:15:00",
      "expires_at": "2026-08-20T20:15:00",
      "preview": {
        "summary": "٢٣ رسالة غياب — جلسة React ١٧ أغسطس",
        "recipient_count": 23,
        "channel": "email",
        "messages": [
          {"trainee_id": 7, "name": "أحمد محمود", "email": "a@x.com",
           "subject": "غيابك عن جلسة React",
           "body": "أهلاً أحمد، لاحظنا غيابك..."}
        ]
      }
    }
  ]
}
```

## المتطلبات — كل واحدة منها مهمة

**١. الأثر واضح قبل الموافقة**
> "٢٣ رسالة هتتبعت لـ ٢٣ شخص" — بخط كبير، فوق الأزرار.

**٢. Preview كامل مش عيّنة**
حاتم لازم يقدر يتصفح الـ ٢٣ رسالة كلها. مش أول واحدة وبس.

**٣. تعديل قبل الإرسال**
```
PATCH /api/approvals/{id}/payload  {edited_content}
```
تعديل رسالة فردية أو القالب كله. أي تعديل بيرجّع الموافقة لحالة معلّقة.

**٤. استبعاد فردي** — checkbox لكل مستقبل.
"وافق عىل ٢٢ من ٢٣" حالة واقعية جدًا.

**٥. رفض بسبب**
```
POST /api/approvals/{id}/reject   {reason}
```

**٦. تحذير الانتهاء** — الموافقات ليها `expires_at`. حذّر قبل ٢٤ ساعة.

**٧. ⚠️ منع الضغط المزدوج**
عطّل الزرار فورًا بعد الضغط + انتظر تأكيد السيرفر.
الباك اند عنده idempotency، بس الواجهة مالهاش لازمة تختبره.

**٨. ممنوع optimistic UI هنا.** استنى الرد الحقيقي.

# المرحلة ٣ (أسبوع ١٣–١٧) — Mission Control

## المكونات

**١. Priority Cards** — كل بطاقة فيها: العنوان، السبب، إجراء واحد واضح.
الـ backend بيرجع `reasoning` لكل بند — **اعرضه**. حاتم لازم يفهم ليه ده الأول.

**٢. Live updates** — WebSocket. لما workflow يخلص، الشاشة تتحدث من غير refresh.

**٣. Charts (Recharts)**
- الحضور عبر الجلسات (line)
- توزيع الحالات لكل جلسة (stacked bar)
- معدل الرد عىل الـ Feedback (line)

**٤. Chat Interface**
```
POST /api/command   {text}
```
- الرد ممكن يكون: تأكيد · سؤال توضيحي · بداية workflow
- **لو جه `clarification_needed`** → اعرض الخيارات كأزرار، مش نص
- اعرض حالة الـ workflow حيًا (جاري تنزيل تقرير Zoom... → حساب المدد...)

**🚪 بوابة المرحلة ٣:** الشاشة بتعرض بيانات حقيقية، والـ demo كاملة
(أمر شات → workflow → موافقة → نتيجة) بتشتغل في ٩٠ ثانية.

## تحذيرات

1. **متستناش الـ API.** عندك mock server من الأسبوع الأول.
2. **الـ RTL مش إضافة في الآخر** — ابدأ بيه من أول component.
3. **شاشة المراجعة أهم من الداشبورد.** استخدامها اليومي أعىل بكتير.
4. **في شاشات الموافقة: الوضوح > الجمال.** دي عمليات حقيقية.
