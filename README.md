# ASROC — نظام إدارة الخدمات الطبية (on-prem)

**نظام داخلي لإدارة رحلة خدمة الموظف الطبية** داخل شركة/مؤسسة، من طلب الكشف إلى الموافقات ثم التشخيص ثم الصيدلية ثم العلاج الشهري والتقارير.

مهم: هذا الـ README مكتوب ليكون **مفهوم لغير المبرمجين** (شرح وظائف + تشغيل + أدوار).

---

## 1) الفكرة ببساطة
تخيل أن الموظف عندما يحتاج كشف طبي يعمل “طلب”.
الطلب يمرّ على عدة مراحل:
1) **مراجعة اعتماد** (مدير/جهة مختصة)
2) **قسم الأمن** (تسجيل خروج/عودة الموظف)
3) **الطبيب** (تشخيص/روشتة/تحويل)
4) **الصيدلية** (صرف الأدوية + إغلاق الروشتة)
5) **العلاج الشهري** (للمعاش/العلاجات المزمنة) + المتابعة
6) في الآخر: **تقارير وإحصائيات** + سجل عمليات (Audit)

---

## 2) الأدوار (Roles) — مين يعمل إيه؟

> كل دور له صلاحيات مختلفة، والواجهة تعرض فقط ما يسمح به الدور.

1. **موظف**: إنشاء طلب كشف طبي + متابعة الحالة
2. **مدير/مكلف (Manager/Office Manager)**: مراجعة طلبات الموظفين (اعتماد/رفض/تأجيل + ملاحظات)
3. **أمن**: تسجيل خروج الموظف للكشف وتسجيل عودة الموظف + تنبيهات عن التأخير
4. **طبيب**: فحص المريض + كتابة الروشتة + إصدار تحويل/إجازة مرضية
5. **صيدلية داخلية**: استقبال الروشتات + صرف الأدوية (متوفر/غير متوفر) + تأكيد الصرف وإغلاق الروشتة
6. **إدارة طبية (Medical Admin)**: مراجعة ومتابعة النظام والتقارير/الحالات
7. **إدارة معاشات (Pension Admin)**: التعامل مع العلاج الشهري وصاحب المعاش
8. **سوبر أدمن (Super Admin)**: إدارة المستخدمين + الأدوار + الصلاحيات + عرض سجل العمليات

---

## 3) كيف يتعامل النظام مع “البيانات”؟ (مسار مبسط)

- **الواجهة (Frontend)**: صفحة عربية على المتصفح، تابعة لأدوار المستخدم.
- **الـ Backend (API)**: سيرفر Node/TypeScript يطبّق قواعد الصلاحيات/الـ workflow.
- **قاعدة البيانات (SQLite)**: تخزن كل شيء داخل ملف قاعدة بيانات على السيرفر (on-prem).

يعني: المستخدم مش بينفّذ من جهازه مباشرة على قاعدة البيانات؛ كل التعديلات تمر عبر الـ API.

---

## 4) التشغيل السريع (Quick Start) — On-Prem / Docker
من جذر المشروع (يشغّل الواجهة + الـ API معًا):

```bash
docker compose up -d
```

ثم:
- الواجهة على: `http://<server-ip>/`
- الـ API داخل السيرفر خلف مسار `/api`
- أول تشغيل بيعمل migrations + يزرع بيانات أولية تلقائيًا.

ملاحظة الأمان: لازم يكون `JWT_SECRET` مضبوط قبل النشر (السيرفر بيرفض القيم الافتراضية).

---

## 5) تشغيل محلي للتطوير (بدون Docker)

### Backend فقط:
```bash
cd api
cp .env.example .env
pnpm install
pnpm prisma:generate
pnpm prisma migrate dev
pnpm db:seed
pnpm dev
```

API عادة على: `http://localhost:4000`

### Frontend فقط:
في terminal تاني من الجذر:
```bash
cp .env.example .env.local
pnpm install
pnpm dev
```

الواجهة عادة على: `http://localhost:5173`

---

## 6) الواجهة (Frontend) — كيف أعرف أين أروح؟
- التنقل يتم عبر **Routes** مع حماية حسب الدور.
- بعد تسجيل الدخول: المستخدم يرى فقط الصفحات التي تخص دوره.

أمثلة مسارات منطقية:
- `/employee` طلباتي ولوحة الموظف
- `/manager/approvals` اعتماد طلبات الموظفين
- `/security` تسجيل الأمن خروج/عودة
- `/doctor` تشخيص/روشتات
- `/pharmacy` صرف الأدوية
- `/medical-admin` و `/pension-admin` للإدارة والمتابعة
- `/super-admin` إدارة المستخدمين والصلاحيات

---

## 7) التقارير وسجل العمليات (Audit)
- النظام يسجل عمليات مهمة (من خانات/انتقالات حالة الطلب) داخل **Audit Logs**.
- Super Admin يقدر يرى سجل العمليات (Last entries) لفهم من فعل ماذا ومتى.

---

## 8) الملاحظات المهمة للمشرف (بدون برمجة)
- تغيير دور/صلاحية أي مستخدم يتم من صفحة **سوبر أدمن**.
- تعطيل حساب المستخدم (isActive=false) يمنع استخدامه فورًا عند الطلبات القادمة.

---

## 9) التقنيات المستخدمة (للمعلومة فقط)
- Frontend: React + TypeScript + Vite + Tailwind + RTL
- Backend: Node + Fastify + Prisma + SQLite
